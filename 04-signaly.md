# Задание 4. Сигналы: SIGTERM против SIGKILL

# Часть А. Упрямый процесс

Сначала был создан скрипт `"~/upryamy.sh"`, который перехватывает сигнал "SIGTERM" и продолжает работу.

Содержимое скрипта:
```
#!/bin/bash
trap 'echo "Получил SIGTERM, но продолжаю работать"' TERM
echo "Мой PID: $$"
while true; do sleep 1; done
```
Скрипт был сделан исполняемым:

`chmod +x ~/upryamy.sh`

После запуска с указанием домашнего каталога:

`~/upryamy.sh &`

процесс получил PID:

`[2] 4337`

Скрипт вывел:

`Мой PID: 4337`

Проверка процесса:

`ps -p 4337 -o pid,stat,cmd`

Результат:
```
    PID STAT CMD
   4337 S    /bin/bash /home/daniil247/upryamy.sh
```
Процесс находился в состоянии "S".

### Отправка SIGTERM

Была выполнена команда:

`kill -TERM 4337`

После этого скрипт вывел:

`"Получил SIGTERM, но продолжаю работать"`

Повторная проверка:

`ps -p 4337 -o pid,stat,cmd`

показала, что процесс всё ещё работает:
```
    PID STAT CMD
   4337 S    /bin/bash /home/daniil247/upryamy.sh
```
Это произошло потому, что в скрипте установлен обработчик "SIGTERM". Получив сигнал, скрипт выполняет указанную команду и продолжает работу.

### Отправка SIGKILL

Затем была выполнена команда:

`kill -KILL 4337`

После этого при проверке процесса его уже не было:
```
[2]+  Killed                  ~/upryamy.sh
```
Таким образом, "SIGKILL" завершил процесс принудительно.

### Почему процесс пережил SIGTERM, но не пережил SIGKILL?

"SIGTERM" является обычным сигналом завершения, который процесс может обработать. В данном случае скрипт перехватывает "SIGTERM" с помощью "trap", выводит сообщение и продолжает работу.

"SIGKILL" завершает процесс принудительно. Обработать или проигнорировать этот сигнал процесс не может, поэтому скрипт был завершён.

### Почему сначала используют SIGTERM, а потом SIGKILL?

Сначала обычно отправляют "SIGTERM", потому что процессу даётся возможность корректно завершиться: закрыть файлы, сохранить данные и освободить ресурсы.

Если процесс не реагирует на "SIGTERM", можно использовать "SIGKILL".

Для базы данных немедленный "kill -9" может привести к некорректному завершению операций и необходимости восстановления после аварийного завершения.

# Часть Б. Передний план и фон

Для проверки управления заданиями оболочки был запущен процесс:

`sleep 600`

Во время его выполнения была нажата комбинация:

`Ctrl+Z`

В терминале появилось:
```
[1]+  Stopped                  sleep 600
```
Затем был запущен ещё один процесс:

`sleep 600`

После чего также была нажата комбинация `"Ctrl+Z"`.

Получилось:
```
[2]+  Stopped                  sleep 600
```
Список заданий:

`jobs`

Результат:
```
[1]-  Stopped                  sleep 600
[2]+  Stopped                  sleep 600
```
Перевод процесса в фон

Командой:

`bg %1`

первый процесс был продолжен в фоновом режиме:

`[1]-  sleep 600 &`

Проверка:

`jobs`

показала:
```
[1]-  Running                  sleep 600 &
[2]+  Stopped                  sleep 600
```
Таким образом, первый процесс продолжил выполнение в фоне, а второй остался остановленным.

### Возврат процесса на передний план

Командой:

`fg %1`

первый процесс был возвращён на передний план:

`sleep 600`

После этого была нажата комбинация:

`Ctrl+C`

Процесс завершился, после чего команда:

`jobs`

показала оставшееся задание:
```
[2]+  Stopped                  sleep 600
```
Оставшийся процесс был завершён командой:

`kill %2`

После проверки:

`jobs`

получен результат:
```
[2]+  Terminated              sleep 600
```
Следовательно, оба процесса "sleep" были завершены.

### Состояние процесса после Ctrl+Z

После "Ctrl+Z" процесс получает состояние "T".

"T" означает, что процесс остановлен.

# Какие сигналы отправляют Ctrl+C и Ctrl+Z?

"Ctrl+C" отправляет процессу сигнал "SIGINT".

"Ctrl+Z" отправляет сигнал "SIGTSTP", который останавливает процесс.
